# Deploying

The API runs on **Render**, the React app on **Vercel**, and the database on **Neon** (PostgreSQL).
Nothing here is deployed by the repository itself; these are the steps to do it by hand. No secret is ever
committed: every credential below is typed into the host's dashboard.

```
Browser ──► Vercel (static React app, frontend/)
   │
   └─ fetch https://<api>.onrender.com/api/...  (CORS: allowed because Render lists the Vercel address)
                         │
                         ▼
                  Render (Node API, backend/) ──► Neon (PostgreSQL)
```

The browser calls the API directly. That is why the API needs `CORS_ORIGIN` and the frontend needs
`VITE_API_URL`. In local development neither is set: the Vite dev server proxies `/api`, so nothing changes there.

## Settings at a glance

| Where | Name | Value |
| --- | --- | --- |
| Render | `DATABASE_URL` | Neon **pooled** connection string (host contains `-pooler`) |
| Render | `DIRECT_URL` | Neon **direct** connection string (same, without `-pooler`). Used only to run migrations |
| Render | `JWT_SECRET` | Generated by Render (`render.yaml` asks for it). Changing it signs everyone out |
| Render | `CORS_ORIGIN` | The Vercel address, e.g. `https://your-app.vercel.app`: scheme and host, no path, no trailing slash needed |
| Render | `PORT` | **Do not set.** Render provides it and the API reads it |
| Vercel | `VITE_API_URL` | The Render address, e.g. `https://car-dealership-api.onrender.com`. Include `https://` |
| Vercel | `VITE_CURRENCY`, `VITE_LOCALE` | Optional, as in `frontend/.env.example` |

## 1. Neon (database)

1. Create a project and a database. Pick a region close to the Render region you will use.
2. From **Connect**, copy two connection strings: the **pooled** one and the **direct** one (turn the "Connection pooling"
   toggle off). Both already carry `sslmode=require`, which is what Neon needs.
3. Nothing to create by hand: the tables, constraints and indexes are built by the migrations in
   `backend/prisma/migrations`, which run during the Render build.

Why two strings: the running API is happy behind Neon's pooler, but `prisma migrate deploy` takes a lock that a
transaction pooler cannot hold. `backend/prisma.config.ts` therefore uses `DIRECT_URL` when it is set (the Prisma CLI,
so migrations) while the API itself only ever reads `DATABASE_URL`. If you would rather use one string, set only
`DATABASE_URL` to the direct address and leave `DIRECT_URL` out.

## 2. Render (API)

Either use the Blueprint or create the service by hand with the same values.

**Blueprint:** Render dashboard → **New → Blueprint** → pick this repository. It reads [`render.yaml`](render.yaml) and
asks you for the three values marked `sync: false`. For `CORS_ORIGIN` you do not know the Vercel address yet; enter a
placeholder and fix it in step 4.

**By hand:** New → Web Service, root directory `backend`, runtime Node, then:

| Field | Value |
| --- | --- |
| Build command | `npm ci --include=dev && npm run build && npm run db:migrate:deploy` |
| Start command | `npm start` |
| Health check path | `/api/health` |
| Environment | `NODE_VERSION=22`, plus the Render rows in the table above |

What the commands do: `npm run build` generates the Prisma client and compiles TypeScript to `backend/dist`;
`npm start` runs `node dist/server.js` (no `tsx` in production); `db:migrate:deploy` applies pending migrations and
nothing else, so it is safe to run on every deploy. A failing migration fails the build, so the old version keeps serving.

`/api/health` answers `{"status":"ok"}` without a login and without touching the database, so a sleeping Neon database
never makes Render think the API is down.

### Create the first administrator (once)

There is no admin through the API on purpose. Run the seed from your own machine against Neon, so the password never
leaves it. In `backend/`, with the **direct** string:

```bash
DATABASE_URL="<neon direct connection string>" ADMIN_EMAIL="you@example.com" ADMIN_PASSWORD="<a strong password>" npm run db:seed
```

It is safe to run again: an existing administrator is left unchanged. Do not put `ADMIN_PASSWORD` in Render.

## 3. Vercel (frontend)

1. New Project → import this repository → set **Root Directory** to `frontend`. The framework is detected as Vite;
   [`frontend/vercel.json`](frontend/vercel.json) pins the build and output.
2. Add `VITE_API_URL` (the Render address) under Environment Variables, for Production and, if you use them, Preview.
   Vite reads it **at build time**, so changing it later needs a redeploy.
3. Deploy. `vercel.json` rewrites every path to `index.html`, so a refresh on any React Router address (for example
   `/login`) loads the app instead of a Vercel 404. Real files such as `/assets/*.js` are still served as themselves.

## 4. Tell the API about the Vercel address

Set Render's `CORS_ORIGIN` to the final Vercel address (it saves and redeploys). Several sites can be allowed by
separating them with commas, for example the production domain and `http://localhost:5173`. Wildcards are refused on
purpose, and the API refuses to start if an entry is not a bare scheme-and-host, so a typo shows up in the deploy logs.

Vercel preview deployments each get their own address, which is not on the list, so they cannot call the API.
That is intended; add one by hand if you need to test a preview.

## Checking it worked

1. `https://<api>.onrender.com/api/health` shows `{"status":"ok"}`.
2. Open the Vercel address: the landing page loads. Refresh on `/login`: it still loads.
3. Create an account, sign in, and see the inventory. In the browser's network tab the calls go to the Render address and
   succeed. A red CORS message in the console means `CORS_ORIGIN` does not match the page's address exactly (check
   `http` vs `https` and the port).
4. Sign in as the administrator and add a vehicle.

## Things to know

- **Free tiers sleep.** Render's free web service stops after a quiet spell and takes up to a minute to wake, and Neon
  suspends an idle database and wakes within seconds. The first request after a break is slow; this is not a fault.
- **Changing `JWT_SECRET`** invalidates every issued token; people sign in again.
- **Rolling back** the API is a redeploy of an earlier commit from Render's dashboard. Migrations are not reversed, so
  keep them backward compatible with the previous release.
- **Local development is unchanged:** `docker compose up -d`, `npm run dev` in `backend/`, `npm run dev` in `frontend/`.
